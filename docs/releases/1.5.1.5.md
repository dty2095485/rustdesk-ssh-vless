## Changes

### Client

- The status line now reports the server-side view of this device:
  `Ready (VLESS) · 服务端已确认` / `· 服务端未确认`, refreshed every 10 s with the
  same `OnlineRequest` the address book already uses. hbbs reports a peer online
  only when it saw a registration within its 30 s window, so this is the state
  other clients see; a local "Ready" no longer hides a stale registration.

### Server (same tag, not part of this Windows installer)

- hbbs accepts a change-id request — the `RegisterPk` with an empty `pk` and an
  `old_id` the client sends when the user changes the ID. Official hbbs answers
  `NOT_SUPPORT`, which the client shows as "server does not support".
  The new id is validated against the same custom-id rule the client uses, the
  caller must present the old id's machine uuid, the row is moved by `guid`
  (keeping `created_at`/`pk`), the in-memory registration follows, and retries
  are idempotent. Normal registration paths are unchanged.

## Server image

- `ghcr.io/dty2095485/rustdesk-server-combined:1.5.1.5` — the combined image
  (RustDesk `hbbs`/`hbbr`/`hbvless`/`hbssh` + 3x-ui panel) with `hbbs` 1.1.17
  carrying the custom-id patch; same image lineage as the VPS1 deployment, so
  load it with `docker load -i …` and use it as a drop-in replacement.
- Sanitized before export: no database, certificate, private key or UUID is
  baked in (`/data` is empty, `/run/tls` is supplied at runtime, no
  credential-like environment variables in the image config).

## Known limits

- `uuid` is the credential for a rename, so knowing a machine's `machine_uid`
  is enough to change its id; there is no separate rate limit on that path.
- The previous id is not kept: peers that still list it keep showing it offline.
- The status indicator polls the rendezvous server's online port directly
  (21115). A failed query is reported as `服务端未确认`, so a red label can also
  mean the query itself could not reach the server.
